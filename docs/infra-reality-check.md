## 1. 아키텍처 복잡도 — 솔직한 평가

| 레이어 | 제안 기술 | 실제 요구 역량 | 중소기업 보유율 |
|--------|-----------|---------------|----------------|
| Frontend | Next.js 15 + PWA + React Native | 숙련 FE 2–3명 | △ |
| Backend | gRPC + NestJS + CQRS + Event Sourcing | 백엔드 시니어 2명 이상 | ✗ (드묾) |
| 인프라 | GKE Autopilot + Istio Service Mesh | DevOps/SRE 전담 1–2명 | ✗ (거의 없음) |
| 배포 | ArgoCD + Blue/Green + Canary + Feature Flags | GitOps 전문가 | ✗ |
| 보안 | BeyondCorp + mTLS + DLP | 보안 아키텍트 | ✗ |
| 모니터링 | Chaos Engineering + Error Budget | SRE 전담 | ✗ |

### 핵심 문제:
- **DDD + CQRS + Event Sourcing** 을 동시에 도입하는 것만으로도 보통 6개월~1년짜리 리팩터링 프로젝트다.
- **Istio Service Mesh**는 Kubernetes 위에서 동작하는 L7 프록시 레이어로, 학습 비용과 운영 난이도가 극히 높다. 넷플릭스·카카오·네이버 수준의 팀에서도 조심스럽게 도입하는 기술이다.
- **Chaos Engineering**(장애를 의도적으로 주입해 내성 테스트)은 SRE 팀이 안정적으로 운영 중일 때 비로소 하는 것이다. Week 7–8에 넣는다는 건 현실과 동떨어져 있다.

## 2. 타임라인 — Week 8 완성의 불가능성

```
Week 1–2: GCP Org + GKE Autopilot + AlloyDB + Istio + Terraform
```
이것만도 경험자 3–4명이 한 달 이상 걸린다.
- GCP Organization 설계 (IAM, VPC, Shared VPC, Billing) → 1–2주
- Terraform으로 GKE + AlloyDB + Istio 프로비저닝 → 2–4주
- Istio 메시 설정 + mTLS + 인그레스 → 1–2주

**현실적 Week 1–2 목표 달성률: 약 15–20%**

```
Week 3–4: 6개 마이크로서비스 분리
```
- auth, edu-content, tenant, analytics, simulation, notification 분리
- 기존 모놀리식 → MSA 전환은 도메인 분석부터 시작해 최소 3–6개월
- Cloud Run + Pub/Sub 연동까지 포함하면 더 길어짐

**현실적 타임라인: 3–6개월 (팀 4–6명 기준)**

## 4. 한국 중소기업의 현실

### 4-1. 인력 수급
- 한국에서 **Kubernetes + Istio + ArgoCD**를 모두 다루는 DevOps 엔지니어는 극히 드물고, 연봉 7,000만~1억 이상이다.
- **gRPC + Event Sourcing**을 실무에서 써본 백엔드 개발자도 상위 10% 이내다.
- 교육 스타트업/중소기업이 이런 인력을 동시에 3–5명 확보하는 건 자금이 있어도 6–12개월이 걸린다.

### 4-2. 운영 리스크
- 이 아키텍처를 올려두고 나서 **온콜(On-Call) 대응**이 가능한 팀이 없다면, 장애 시 수습 능력이 없다.
- Istio + GKE 장애는 AWS EC2 장애보다 훨씬 복잡하다. 네트워크 레이어가 추상화된 만큼 디버깅 난이도가 높다.
- **운영 복잡도 ∝ 이직 리스크**: 핵심 DevOps 1명이 나가면 전체 인프라 운영이 블랙박스가 된다.

### 4-3. 한국 교육 고객 특성
- 한국 학교·교육기관은 **IDC 기반 온프레미스 또는 KT·SKT 클라우드**를 선호하는 경우가 많다.
- 교육부 관련 조달은 국내 클라우드(CSAP 인증) 우선 정책이 있어, GCP만으로는 공공 조달에 불리할 수 있다.
- 학교 IT 담당자 입장에서 "Google Cloud 기반 글로벌 CDN 멀티리전"은 장점이 아닌 **블랙박스**로 인식될 수 있다.

## 5. 투자 유치용 vs. 실행 계획의 괴리

이 문서의 아키텍처가 **투자자 대상 피치덱**으로 쓰인다면:
- ✅ 비전과 확장성 어필에 효과적
- ✅ 기술 이해도 높은 투자자에게 신뢰감
- ✅ 경쟁사와 차별화 포인트 명확

그러나 **실제 실행 로드맵**으로 쓰인다면:
- ❌ 8주 타임라인은 투자자 기대치와 현실 사이에 위험한 괴리를 만든다
- ❌ 팀이 없는 상태에서 이 복잡도의 인프라를 올리면 기술 부채가 아니라 기술 폭탄이 된다
- ❌ $1,200/월 추정은 실제 청구서를 받으면 신뢰 문제로 이어질 수 있다

## 6. 내 권고 — 현실적 단계별 접근

### Phase 1: 지금 ~ 서비스 안정화 (0–3개월)
```
현 스택 유지: React + Vite + Supabase
→ 충분히 훌륭한 스택이다. 10K 사용자까지는 이걸로도 된다.
→ 지금 당장 Kubernetes가 필요한 시점이 아니다.
```

### Phase 2: PMF 확인 후 (3–9개월)
```
Vercel 또는 Cloudflare Pages (Frontend)
Supabase Pro → Railway 또는 Fly.io (Backend)
Cloud Run (마이크로서비스 분리 필요 시 일부만)
```

### Phase 3: 실제 스케일링이 필요할 때 (9–18개월)
```
GKE (Autopilot) 도입 검토
Cloud SQL → AlloyDB 마이그레이션 검토
MSA 부분 분리 (auth 서비스부터)
```

### Phase 4: Google급 아키텍처 (18개월+, 팀 10명+)
```
위 제안 아키텍처가 현실적인 타겟이 되는 시점
이때는 전담 SRE + DevOps 팀이 반드시 필요
```

투자자들은 "지금 당장 Google이다"보다 "명확한 단계별 로드맵과 현실 인식"을 더 높이 평가하는 경우가 많다.
특히 B2B 교육 SaaS 도메인에서는 **실행력과 현실적 판단력**이 기술 스펙보다 중요한 투자 기준이 된다.
