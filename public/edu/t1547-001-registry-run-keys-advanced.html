#1. CLSID 하이재킹 (COM Hijacking)

🔩

COM 오브젝트와 CLSID

COM(Component Object Model) 오브젝트는 Windows에서 소프트웨어 컴포넌트 간 통신을 위한 표준 인터페이스입니다. 각 COM 오브젝트는 CLSID(Class Identifier)라는 고유 GUID로 식별됩니다. Windows는 CLSID를 레지스트리에서 검색하여 해당 DLL 또는 EXE를 로드합니다. 공격자는 이 조회 순서를 악용하여 악성 DLL을 로드시킵니다.

com_hijack.ps1
powershell
⚠️ 교육 목적 코드 — COM 하이재킹 원리 분석
# COM 오브젝트 조회 순서:
# 1) HKCU\Software\Classes\CLSID\{GUID} ← 공격자 삽입!
# 2) HKLM\Software\Classes\CLSID\{GUID} ← 원본 DLL
# 예: 자주 호출되는 COM 오브젝트 하이재킹
$clsid = '{b5f8350b-0548-48b1-a6ee-88bd00b4a5e7}'
# HKCU에 하이재킹 엔트리 생성
$regPath = "HKCU:\Software\Classes\CLSID\$clsid\InProcServer32"
New-Item -Path $regPath -Force
Set-ItemProperty -Path $regPath -Name '(Default)' `
-Value 'C:\Users\Public\malicious.dll'
Set-ItemProperty -Path $regPath -Name 'ThreadingModel' `
-Value 'Both'

⚠️ COM 하이재킹의 위험성

COM 하이재킹은 Run 키와 달리 Autoruns의 기본 필터에 잘 잡히지 않으며, 정상 Windows 프로세스(explorer.exe 등)가 악성 DLL을 로드하므로 행위 기반 탐지도 어렵습니다. EDR이 잡기 어려운 고급 지속성 기법입니다.

#2. DLL Search Order Hijacking via Registry

📦

DLL 검색 순서와 레지스트리 악용

Windows는 DLL을 로드할 때 특정 순서로 경로를 검색합니다. KnownDLLs 레지스트리 키에 등록되지 않은 DLL은 이 검색 순서를 따릅니다. 공격자는 레지스트리를 수정하여 정상 DLL 대신 악성 DLL이 먼저 로드되도록 조작합니다.

dll_hijack_analysis.ps1
powershell
⚠️ 교육 목적 코드 — DLL 하이재킹 분석용
# Windows DLL 검색 순서 분석
# 1. KnownDLLs 레지스트리 확인
# 2. 애플리케이션 디렉토리
# 3. System32 → System → Windows → PATH
# KnownDLLs에 등록된 DLL 목록 확인
$knownDlls = Get-ItemProperty -Path `
'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs'
# KnownDLLs에 없는 DLL = 하이재킹 가능 대상
$knownDlls.PSObject.Properties | Where-Object {
$_.Name -notlike 'PS*'
} | ForEach-Object {
Write-Host "Protected: $($_.Name) = $($_.Value)"
}

#3. COM 오브젝트 지속성 심화

🎭

TreatAs 및 ScriptletURL 하이재킹

COM 하이재킹에는 InProcServer32 외에도 여러 변형이 존재합니다: ① TreatAs 키 — CLSID를 다른 CLSID로 리다이렉션. ② ScriptletURL — COM 오브젝트가 로드될 때 원격 URL에서 스크립틀릿을 실행. ③ ProgID 하이재킹 — 애플리케이션이 ProgID로 COM을 호출할 때 CLSID 매핑을 조작.

taskscheduler_com_hijack.ps1
powershell
⚠️ 교육 목적 코드 — 실제 APT가 사용하는 기법
# Task Scheduler COM 하이재킹
# 이 CLSID는 Task Scheduler가 정기적으로 호출함
$clsid = '{0f87369f-a4e5-4cfc-bd3e-73e6154572dd}'
$path = "HKCU:\Software\Classes\CLSID\$clsid\InProcServer32"
# HKCU에 오버라이드 생성 (HKLM보다 우선)
New-Item -Path $path -Force | Out-Null
Set-ItemProperty -Path $path `
-Name '(Default)' -Value 'C:\payload.dll'
# Task Scheduler가 다음 실행 시 payload.dll 로드
# explorer.exe가 부모 프로세스 → 정상으로 보임
🔍

COM 하이재킹 자동 검색

HKCU\Software\Classes\CLSID에 InProcServer32 키가 존재하면 하이재킹 가능성이 높습니다. 정상적으로 이 위치에 COM 엔트리를 등록하는 소프트웨어는 드물기 때문입니다. Autoruns에서 'Everything' 탭으로 이 위치를 확인할 수 있습니다.

#4. 포렌식 아티팩트: NTUSER.DAT 분석

📡

NTUSER.DAT — 사용자 레지스트리 하이브

NTUSER.DAT는 각 사용자의 HKCU 레지스트리 하이브를 디스크에 저장한 파일입니다. 위치: C:\Users\<username>\NTUSER.DAT. 오프라인 포렌식에서 이 파일을 분석하면 Run 키, COM 하이재킹, 최근 실행 기록 등을 확인할 수 있습니다.

regripper_analysis.bat
batch
⚠️ 교육 목적 코드 — 포렌식 분석 도구
REM RegRipper를 이용한 NTUSER.DAT 포렌식 분석
REM 1단계: Run 키 분석 플러그인 실행
rip.exe -r C:\evidence\NTUSER.DAT -p run
REM 2단계: 자동 실행 관련 항목 분석
rip.exe -r C:\evidence\NTUSER.DAT -p autorun
REM 3단계: COM 하이재킹 흔적 분석
rip.exe -r C:\evidence\NTUSER.DAT -p clsid
REM 4단계: 전체 프로파일링
rip.exe -r C:\evidence\NTUSER.DAT -a > full_report.txt

#5. ShimCache & AmCache 분석

🕵️

실행 흔적 추적: ShimCache와 AmCache

ShimCache(Application Compatibility Cache)는 실행된 적 있거나 시스템이 인식한 실행 파일의 경로와 타임스탬프를 기록합니다. AmCache는 더 상세한 메타데이터(SHA1 해시, PE 헤더 정보)를 포함합니다. 두 아티팩트를 결합하면 악성코드의 실행 이력을 정확하게 재구성할 수 있습니다.

포렌식 아티팩트 비교

아티팩트위치핵심 정보분석 도구

#6. YARA 규칙: 자동 실행 악성코드 탐지

🎯

레지스트리 조작 악성코드 YARA 탐지

YARA 규칙으로 Run 키를 조작하는 악성코드 바이너리 자체를 탐지할 수 있습니다. 악성코드 내부에는 'CurrentVersion\Run', 'RegSetValueEx' 등의 문자열이 포함되어 있어 패턴 매칭으로 탐지합니다.

detect_registry_persistence.yar
yara
⚠️ 교육 목적 코드 — YARA 탐지 규칙
rule Registry_Persistence_Malware {
meta:
author = "GOTROOT EDU"
description = "Detects malware modifying Run keys"
severity = "high"
strings:
$reg1 = "CurrentVersion\\Run" ascii wide
$reg2 = "Software\\Classes\\CLSID" ascii wide
$api1 = "RegSetValueEx" ascii
$api2 = "RegCreateKeyEx" ascii
condition:
uint16(0) == 0x5A4D and // PE 파일
(1 of ($reg*)) and (1 of ($api*))
}

#7. 엔터프라이즈 방어: GPO & SIEM 연동

🏢

그룹 정책(GPO)으로 자동 실행 제한

Active Directory 환경에서 GPO를 통해 Run 키 사용을 제한할 수 있습니다. AppLocker와 WDAC을 결합하면 허용된 프로그램만 실행 가능하며, SIEM 연동을 통해 실시간 탐지 체계를 구축합니다.

splunk_detection.spl
splunk
⚠️ 교육 목적 코드 — SIEM 탐지 규칙
| Splunk SPL: 레지스트리 Run 키 변경 탐지 |
index=sysmon EventCode=13
TargetObject="*\\CurrentVersion\\Run*"
NOT Image IN (
"C:\\Program Files*",
"C:\\Windows\\System32*"
)
| stats count by Image, TargetObject, Details
| COM 하이재킹 탐지 |
index=sysmon EventCode=13
TargetObject="*\\Classes\\CLSID\\*InProcServer32*"
TargetObject="HKU\\*"
| table _time, Image, TargetObject, Details

#Q. 종합 퀴즈

Q1. COM 하이재킹에서 HKCU가 HKLM보다 우선 적용되는 이유는?

💡 Windows COM 런타임은 HKCU를 먼저 검색하고, 없으면 HKLM을 확인합니다. 이 조회 순서 덕분에 관리자 권한 없이도 하이재킹이 가능합니다.

Q2. RegRipper 'run' 플러그인이 확인하는 항목은?

💡 RegRipper의 'run' 플러그인은 NTUSER.DAT에서 Run/RunOnce 키의 모든 값을 추출합니다.

Q3. ShimCache와 AmCache의 핵심 차이점은?

💡 AmCache는 SHA1 해시, PE 헤더 정보 등 더 상세한 메타데이터를 포함하여 포렌식 분석에 더 유용합니다.

Q4. YARA 규칙에서 'uint16(0) == 0x5A4D'의 의미는?

💡 0x5A4D는 'MZ'로 PE 실행 파일의 매직 바이트입니다. 분석 대상이 실행 파일인 경우에만 규칙을 적용합니다.

Q5. COM 하이재킹이 Run 키보다 탐지가 어려운 이유는?

💡 explorer.exe 같은 정상 프로세스가 하이재킹된 DLL을 로드하므로 행위 기반 탐지에서 정상으로 보입니다.

Q6. GPO 'Do not process the run once list'의 효과는?

💡 이 정책은 RunOnce 키의 자동 실행을 차단하여 1회성 페이로드 실행을 방지합니다.

Q7. Splunk COM 하이재킹 탐지 핵심 필터 조건은?

💡 Event ID 13에서 Classes\CLSID와 InProcServer32가 포함되고 HKU에 위치하면 COM 하이재킹입니다.

Q8. 근본 원인 분석(Root Cause Analysis)이 중요한 이유는?

💡 지속성을 제거해도 초기 침투 경로가 열려 있으면 공격자가 재침투하여 새로운 지속성을 설치합니다.
