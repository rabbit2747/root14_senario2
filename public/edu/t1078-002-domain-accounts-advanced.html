#1. Kerberos 프로토콜 Deep Dive

🎫

Kerberos: 티켓 기반 인증의 핵심

초급 과정에서 "호텔 티켓"으로 비유한 Kerberos. 이제 기술적 세부사항을 파고듭니다. Kerberos는 3자 인증(Three-party authentication) 모델입니다.

👤
Client
사용자 (서비스 요청자)
🏛️
KDC (Key Distribution Center)
도메인 컨트롤러 (티켓 발급소)
🖥️
Service Server
SQL, Exchange, IIS 등

TGT → TGS 인증 흐름

1️⃣
AS-REQ
사용자 → KDC: "저는 Alice입니다. 로그인하고 싶습니다."
사용자의 비밀번호 해시로 암호화된 타임스탬프 전송 (사전인증)
2️⃣
AS-REP
KDC → 사용자: "확인됐습니다. TGT(Ticket Granting Ticket)를 드립니다."
TGT는 KDC의 krbtgt 계정 해시로 암호화 → 사용자가 열어볼 수 없음
3️⃣
TGS-REQ
사용자 → KDC: "TGT 가져왔습니다. SQL 서버에 접속하고 싶어요." (SPN 지정)
SPN = MSSQLSvc/SQLSERVER01.corp.local:1433
4️⃣
TGS-REP
KDC → 사용자: "서비스 티켓(TGS)을 드립니다."
⚠️ 핵심: 이 TGS는 서비스 계정의 비밀번호 해시로 암호화되어 있습니다!
🔥
Kerberoasting의 핵심 취약점

KDC는 TGS 요청 시 사용자에게 권한 검증 없이 티켓을 발급합니다. 즉, 아무런 권한이 없는 일반 직원(Domain User)도 모든 서비스의 TGS를 요청할 수 있고, 이 티켓은 서비스 계정의 비밀번호로 암호화되어 있으므로 오프라인에서 크래킹이 가능합니다.

암호화 유형 비교: RC4 vs AES

💀 RC4-HMAC (etype 23)
  • • NTLM 해시 기반 → 크래킹 매우 빠름
  • • 초당 수억 개 비밀번호 대입 가능
  • • hashcat 모드: 13100
  • → 8자리 비밀번호 = 수 시간 내 크래킹
🛡️ AES256-CTS (etype 18)
  • • 솔트(Salt) + 4096회 반복 해싱
  • • 크래킹 속도 RC4 대비 1/100
  • • hashcat 모드: 19700
  • → 동일 비밀번호라도 크래킹 수백 배 어려움

#2. Kerberoasting 공격 전 과정

⚔️

공격 5단계 상세

🔎 Phase 1

대상 식별 (SPN 열거)

LDAP 쿼리 또는 GetUserSPNs.py로 SPN이 설정된 서비스 계정을 목록화합니다. 특히 Domain Admin 그룹 소속이거나 비밀번호 변경일이 오래된 계정을 우선 타겟으로 삼습니다.

🎫 Phase 2

TGS 티켓 요청

Rubeus, Impacket, 또는 기본 Windows API(KerberosRequestorSecurityToken)로 대상 SPN의 TGS를 요청합니다. 이 과정은 완전히 합법적인 Kerberos 동작이므로 기본 보안 장비로는 탐지가 어렵습니다.

📦 Phase 3

티켓 추출 (Export)

획득한 TGS를 Hashcat/John 호환 형식으로 추출합니다. Rubeus는 /format:hashcat 옵션으로 바로 크래킹 가능한 포맷을 출력합니다.

🔓 Phase 4

오프라인 크래킹

공격자의 개인 장비에서 Hashcat + GPU로 대입 공격을 수행합니다. 네트워크와 완전히 분리되어 있으므로 계정 잠금(lockout) 없이 무제한 시도가 가능합니다.

# hashcat 크래킹 명령
$ hashcat -m 13100 ticket.hash rockyou.txt -r rules/best64.rule
Speed: 234.5 MH/s (RC4) | Status: Cracked | Password: Summer2026!
👑 Phase 5

권한 상승 및 횡이동

크래킹된 비밀번호로 서비스 계정에 로그인하여 횡이동(Lateral Movement)을 수행합니다. 서비스 계정은 대부분 관리자 그룹에 속해 있거나, 여러 서버에 접근 권한을 갖고 있어 공격이 급속히 확산됩니다.

실전 도구 비교

도구 환경 특징 탐지 난이도
Rubeus Windows (C#) 인메모리 실행, 다양한 공격 모듈 어려움
Impacket Linux (Python) 원격 실행, 네트워크 기반 보통
PowerView Windows (PS) PowerShell 스크립트, AMSI 우회 필요 쉬움
.NET API Windows Windows 기본 API 사용, 도구 설치 불필요 매우 어려움

#3. 탐지·방어·실전 대응

📡

탐지: 이벤트 ID 4769 분석

Kerberoasting의 가장 핵심적인 탐지 포인트는 이벤트 4769 (Kerberos Service Ticket Operations)입니다. 정상적인 TGS 요청과 공격을 구분하는 핵심 필드를 분석합니다.

// 의심스러운 4769 이벤트 패턴
Event ID: 4769
Service Name: MSSQLSvc/SQLSERVER01
Ticket Encryption Type: 0x17 (RC4-HMAC) ← 핵심 지표!
Client Address: 10.10.15.42 (워크스테이션)
Ticket Options: 0x40810000
// 정상 패턴과의 차이점:
// 1. RC4(0x17) 요청 → 현대 환경에서는 AES(0x12)가 기본
// 2. 동일 IP에서 짧은 시간 내 다수 서비스 티켓 요청
// 3. 서비스에 실제 접속하지 않고 티켓만 요청

방어 전략 3단계

1 예방 (Prevention)

  • • AES 강제 전환: GPO에서 RC4 비활성화, 서비스 계정에 AES256 강제
  • • gMSA (Group Managed Service Account) 도입: 120자 무작위 비밀번호 자동 회전
  • • 서비스 계정 비밀번호 최소 25자 + 90일 회전 정책
  • • 서비스 계정을 관리자 그룹에서 제거 (최소 권한 원칙)

2 탐지 (Detection)

  • • 4769 이벤트에서 Encryption Type = 0x17 (RC4) 필터링
  • • 동일 계정의 짧은 시간 내 다수 TGS 요청 (임계값: 10건/5분)
  • • 허니팟 SPN 계정 설정: 실제로 사용하지 않는 서비스에 SPN 등록 → 누군가 티켓을 요청하면 즉시 알림
  • • MDI (Microsoft Defender for Identity) 또는 CrowdStrike의 Kerberoasting 탐지 룰 활용

3 대응 (Response)

  • • 즉시 해당 서비스 계정 비밀번호 변경 + 세션 강제 종료
  • • 서비스 계정이 접근한 모든 시스템의 로그 분석 (횡이동 확인)
  • • Golden Ticket 가능성 평가: krbtgt 계정 비밀번호도 변경 검토
  • • 포렌식: 공격자의 최초 침입 경로 역추적
